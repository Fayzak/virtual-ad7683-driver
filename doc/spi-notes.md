# Основные моменты про SPI
Описание используемых сигналов:
- MOSI — Master Output, Slave Input (выход ведущего, вход ведомого). Данный сигнал предназначен для последовательной передачи данных от ведущего к ведомому. На ведомой микросхеме это SDI, DI (вход), на ведущем — SDO, DO (выход).
- MISO — Master Input, Slave Output (вход ведущего, выход ведомого). Данный сигнал предназначен для последовательной передачи данных от ведомого к ведущему. На ведомой микросхеме это SDO, DO (выход), на ведущем — SDI, DI (вход).
- SCK — Serial Clock (сигнал синхронизации). Формируется ведущим и используется для синхронизации при передаче данных. Также может иметь название SCLK, CLK и др.
- ~CS — Chip Select (выбор микросхемы). С помощью данного сигнала происходит активация ведомого устройства. Обычно он является инверсным, то есть низкий уровень считается активным. Иногда его называют ~SS (Slave Select, рус. «выбор ведомого»).

Несколько устройств могут разделять SCLK, MOSI и MISO, но обычно имеют отдельные CS. За один такт возможны одновременно передача и прием бита (full duplex); при чтении ведущий тоже должен формировать такты.

Существует четыре режима работы SPI устройств, которые представляют собой комбинацию двух бит:
- CPOL (Clock Polarity) — определяет начальный уровень (полярность) сигнала синхронизации.
CPOL=0 показывает, что сигнал синхронизации начинается с низкого уровня, так что передний фронт является нарастающим, а задний — падающим.
CPOL=1, сигнал синхронизации начинается с высокого уровня, таким образом передний фронт является падающим, а задний — нарастающим.
- CPHA (Clock Phase) — фаза синхронизации, определяет по какому из фронтов синхронизирующего сигнала производить выборку данных.
CPHA=0 показывает что необходимо производить выборку по переднему фронту, а
CPHA=1 показывает что выборку данных необходимо производить по заднему фронту.

Номер режима равен `2 * CPOL + CPHA`: mode 0 — 0/0, mode 1 — 0/1, mode 2 — 1/0, mode 3 — 1/1. Передний фронт означает первый переход от уровня покоя, а не обязательно нарастающий. Данные должны быть стабильны к моменту выборки; нужный режим выбирается по временной диаграмме микросхемы.

# SPI в ядре Linux
- Драйвер контроллера управляет SPI-блоком компьютера или платы (заставляет оборудование работать определенным способом)
- Драйвер протокола знает правила конкретной микросхемы (определает как должно работать оборудование)

Основной путь:
1. Регистрация контроллера, который обслуживает запросы SPI драйвера протокола. Для отдельного виртуального стенда он может выдавать тестовые данные вместо работы с физической шиной.
    - `struct spi_controller` - описание контроллера: возможности, число CS и функции выполнения передач
    - `spi_alloc_host()` - выделение контроллера хоста
    - `spi_controller_get_devdata()` - доступ к приватным данным, выделенным вместе с контроллером
    - `spi_register_controller()` - публикация в системе; `spi_unregister_controller()` - удаление
    - `setup`, `cleanup`, `prepare_transfer_hardware`, `unprepare_transfer_hardware`, `transfer_one` или `transfer_one_message` - функции контроллера

2. Создание устройств, подключенных к контроллеру. SPI обычно не обнаруживает микросхемы автоматически: системе заранее сообщают, что подключено к каждому CS.
    - `struct platform_device` - один из способов представить сам контроллер и его ресурсы, например физические адреса и IRQ
    - `struct spi_device` - конкретная периферия на контроллере: CS, режим, максимальная частота и имя для сопоставления с драйвером; указатель `controller` связывает ее с `spi_controller`
    - Device Tree или ACPI - описание периферии, по которому SPI core создает `spi_device` при регистрации контроллера
    - `struct spi_board_info` и `spi_register_board_info()` - альтернативное описание устройств таблицей в коде платы
    - `spi_new_device()` - программное создание устройства на уже зарегистрированном контроллере, `spi_unregister_device()` - его удаление

3. Регистрация драйвера протокола и привязка к устройству
    - `struct spi_driver` - драйвер конкретной микросхемы с функциями `probe` и `remove`; регистрация через `spi_register_driver()` или `module_spi_driver()`
    - `spi_match_device()` - выбирает драйвер: сначала `driver_override`, затем OF (`compatible`), ACPI, `id_table` по `modalias`; если `id_table` нет - сравнение `modalias` с именем драйвера
    - После совпадения device core запускает обертку SPI core `spi_probe()`, которая вызывает `spi_driver.probe(struct spi_device *spi)`. Это происходит при появлении устройства или драйвера; первым может быть зарегистрирован любой из них
    - `probe` - инициализирует периферию, выделяет ее приватные данные, сохраняет их через `spi_set_drvdata()`; уже здесь разрешены SPI-запросы. Возвращает 0 при успехе или отрицательный код ошибки
    - `remove` - драйвер останавливает источники новых запросов, дожидается своих незавершенных операций и освобождает ресурсы. После возврата из `remove` или ошибки `probe` он не должен отправлять новые сообщения
    - `spi_setup()` - применяет режим, размер слова и частоту. Начальную настройку выполняет SPI core при добавлении устройства; драйвер может изменить ее через `spi_setup()` в `probe` до первого запроса или позже, когда нет ожидающих сообщений

Итого: `spi_controller` обслуживает шину → `spi_device` описывает периферию на ней → подходящий `spi_driver` управляет этой периферией.

# Передача данных
- `struct spi_message` - запрос к одному `spi_device`, содержащий последовательность `spi_transfer`. Передачи внутри сообщения не перемежаются с другими сообщениями на контроллере.
- `struct spi_transfer` - один участок обмена: `tx_buf`, `rx_buf`, `len` в байтах, при необходимости `speed_hz`, `bits_per_word` и задержки. `speed_hz = 0` использует частоту устройства, ограниченную его `max_speed_hz` и возможностями контроллера.
- Если заданы оба буфера, передача и прием идут одновременно, по `len` байт в каждом направлении. При `rx_buf = NULL` входящие данные отбрасываются; при `tx_buf = NULL` для чтения передаются нули.
- CS обычно активен на протяжении всего сообщения и снимается после последней передачи. `cs_change` позволяет изменить это поведение, например переключить CS между передачами.

Синхронный запрос:
1. Обнулить `spi_transfer`, задать буферы и `len`; инициализировать сообщение через `spi_message_init()`.
2. Добавить передачи через `spi_message_add_tail()` в нужном порядке.
3. Вызвать `ret = spi_sync(spi, &message)`. Функция возвращается после завершения запроса или ошибки его подачи.
4. Проверить `ret`: 0 - успех, отрицательное значение - код ошибки, например `-EINVAL` для неверных параметров или `-EIO` при ошибке обмена. Это не число байт; `message.actual_length` содержит число фактически переданных байт. При ошибке возможна частично выполненная передача, поэтому весь RX нельзя считать корректным.

У SPI нет общего подтверждения приема (ACK): `ret = 0` сам по себе не доказывает наличие микросхемы или правильность ее ответа. Это проверяется по протоколу конкретного устройства.

Буферы и контекст:
- TX/RX - память ядра, пригодная для DMA, например выделенная через `kmalloc()`. Нельзя передавать пользовательский указатель, буфер на стеке или в статической памяти модуля. Размер каждого заданного буфера должен быть не меньше `len`.
- Сами `spi_message` и `spi_transfer` - метаданные: их можно разместить на стеке для `spi_sync()`. Они и буферы должны оставаться действительными и не переиспользоваться до возврата функции.
- При `bits_per_word = 8` два байта результата еще нужно собрать в число по протоколу микросхемы. При `bits_per_word = 16` буфер содержит 16-битные слова в порядке байтов CPU; `len` по-прежнему измеряется в байтах. Порядок битов на проводе и порядок байтов в памяти - разные вещи.
- `spi_sync()` может спать: допустим из `probe`, обработчика файловой операции или worker, но не из IRQ, callback текущего `hrtimer` или под spinlock. У API нет общего тайм-аута ожидания; ожидание не прерывается сигналом. Перевод вызова в worker потребует отдельно решить, что делать при пропуске периодов или занятом worker.
- `spi_async()` допускается из IRQ и контекста задачи; возвращает результат подачи, а не итог обмена. При успешной подаче завершение приходит в `message.complete(message.context)`, итог - в `message.status`. Callback не должен спать; метаданные и буферы должны жить до завершения callback. При ошибке подачи callback не ожидается.
- Если контроллер реализует `transfer_one_message()`, он выставляет `message.status`, обновляет `actual_length` и вызывает `spi_finalize_current_message()`. Для `transfer_one()` возврат 0 означает завершение, отрицательный код - ошибку, 1 - работу в процессе с последующим `spi_finalize_current_transfer()`; сообщение завершает SPI core. Эти finalize-функции вызывает сторона контроллера, а не драйвер периферии.
