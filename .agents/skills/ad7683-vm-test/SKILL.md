# Проверка AD7683 в VM

В начале работы сообщи пользователю, что используешь `ad7683-vm-test`,
и дай ссылку на этот файл. Скилл организует проверку; его выбор не даёт
дополнительных разрешений на команды.

## Среда и разрешения

- Прочитай актуальный `AGENTS.md` в корне проекта: он задаёт целевое ядро,
  команды, ограничения ABI и формат отчёта. Не меняй драйвер в рамках
  одного лишь запроса на проверку.
- Получи SSH-адрес, пользователя, путь рабочей копии VM, 9p-тег и точку
  монтирования из текущего контекста или локальных настроек пользователя.
  Если этих данных нет, запроси недостающее. Не записывай адреса, пароли,
  ключи или SSH-сокеты в репозиторий.
- Перед каждой привилегированной командой получи отдельное разрешение,
  как требует `AGENTS.md`. Не объединяй несколько sudo-действий в скрипт
  или root-shell. Сначала диагностируй ошибку обычной команды.
- Пароль вводит пользователь в защищённом интерактивном окне/терминале.
  При наличии можно использовать `ssh-askpass`. Не проси присылать пароль
  в чат, не сохраняй его в файле, аргументах или переменных окружения.
  Если такого ввода нет, останови зависимые действия и объясни ограничение.
- Не отключай проверку SSH host key. Обход системного SSH-конфига и
  изменение владельца каталога допустимы только после диагностики;
  это не обязательные шаги каждого запуска.

## Подготовка рабочей копии

1. Подключись к VM и проверь `uname -r`, наличие соответствующего дерева
   сборки и состояние модуля. При несовпадении с целевым ядром не загружай
   модуль. Не перезагружай и не перенастраивай VM без отдельной задачи.
2. Проверь `findmnt` для точки 9p: правильные источник, тип и режим записи.
   Подходящее существующее монтирование используй повторно. Если требуется
   монтирование, согласуй команду вида
   `sudo mount -t 9p TAG MOUNTPOINT -o trans=virtio,version=9p2000.L,uid=1000,gid=1000,rw`;
   используй реальные параметры VM, а не слепо UID/GID из примера.
3. Проверь общую папку и каталог назначения. Копируй нужные исходники,
   Makefile/Kbuild и тесты в рабочую копию VM, не перенося `.git`, локальные
   настройки и артефакты сборки. Не удаляй существующие файлы автоматически.
   У существующего каталога `cp -r shared/ work/` создаёт `work/shared`:
   явно проверь итоговые пути и совпадение нужных файлов, например `cmp`.
4. Перейди в рабочую копию VM; дальнейшие сборочные и тестовые команды
   выполняй оттуда. При недостаточных правах сначала покажи владельца
   и согласуй узкое исправление. Не заменяй обычную сборку на sudo-сборку.

## Сборка и проверка

1. Выполни `make build` без sudo (при необходимости с `KERNEL_DIR`).
   Проверь код возврата и `modinfo -F vermagic` собранного модуля;
   утилита может находиться в `/usr/sbin`. При ошибке сборки не продолжай
   загрузку старого `.ko`.
2. Если модуль уже загружен, не считай его артефактом этой сборки и не
   выгружай автоматически: выясни его происхождение и согласуй замену.
   Не закрывай чужие дескрипторы и не завершай чужие процессы.
3. До загрузки сохрани boot ID (`/proc/sys/kernel/random/boot_id`) и
   снимок `dmesg --raw --color=never`. Для чтения журнала сначала попробуй
   обычную команду; sudo используй по отдельному разрешению. Не очищай
   кольцо `dmesg`. Если журнал недоступен, явно отметь эту проверку NOT RUN.
4. Согласуй и выполни `sudo make run`. Проверь наличие `/dev/ad7683`
   и `clients: 0` в `/proc/ad7683` перед тестом. При посторонних клиентах
   не запускай тест, меняющий общую частоту.
5. Согласуй и выполни `sudo python3 test/read_clients.py`. Оцени код
   возврата и фактический вывод, не зашивай число этапов. Проверка пилы
   должна охватывать шаг +1 и wrap, контролировать overruns; она не
   доказывает точность частоты таймера. Локальные проверки Python или
   искусственные потоки не заменяют запуск на драйвере.
6. Даже после сбоя проверь клиентов и восстановление частоты. Если модуль
   загружен нами и клиентов нет, согласуй `sudo make remove`. Не выгружай
   его при активных клиентах. Закрой созданное нами SSH-соединение;
   монтирование и VM оставь в исходном состоянии, не размонтируй чужое.
7. После теста и очистки получи второй снимок журнала и boot ID. При
   смене boot ID сравнение не подтверждает отсутствие ошибок. В одном
   boot запусти локально:

   ```sh
   python3 scripts/compare_kernel_logs.py before.log after.log
   ```

   Путь скрипта отсчитывается от каталога этого скилла. Снимки держи вне
   репозитория. Код 0: исходный снимок сохранён, признаков новых WARN/Oops
   не найдено; 1: найдены подозрительные сообщения; 2: сравнение неполное
   или входные данные непригодны. При коде 2 отсутствие ошибок — NOT RUN,
   а не PASS. Просмотри все новые строки: поиск по шаблонам не заменяет
   оценку журнала. Taint от внешнего/неподписанного модуля сообщай отдельно
   от WARN/Oops.

## Отчёт и диагностика

Сообщи ядро, рабочий каталог, фактически выполненные проверки и итоговое
состояние модуля, клиентов и частоты. Каждую проверку представь таблицей
`команда/случай | PASS/FAIL/NOT RUN | подробности`. Укажи первоначальные
сбои и результат повторения; никогда не объявляй невыполненный шаг успешным.
При отказе в разрешении не повторяй ту же команду другим способом.

Для нестандартной ситуации открой [примеры решений](references/scenarios.md).
Для проверки самого помощника, без SSH и sudo:

```sh
python3 scripts/test_compare_kernel_logs.py
```
